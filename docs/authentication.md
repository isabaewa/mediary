# Регистрация, вход и ограничение доступа

Реализация Django Authentication: UserCreationForm создаёт пользователя и хеширует пароль; AuthenticationForm проверяет логин и пароль; LoginView выполняет вход, logout очищает сессию. Смена пароля — стандартный PasswordChangeView.

## Файлы
- diary/forms.py: SignUpForm и SignInForm.
- diary/auth_views.py: регистрация, вход, выход и срок входа.
- diary/urls.py: accounts/signup/, accounts/login/, accounts/logout/, accounts/password/change/.
- templates/registration/: формы.
- diary/models.py: owner у Medication и HealthEntry; приём принадлежит владельцу связанного препарата.
- diary/views.py: login_required и фильтры owner=request.user, в том числе для прямых ссылок и POST. QuickIntakeForm получает user и предлагает только его препараты.

Запись самочувствия уникальна по паре владелец + дата. Разные пользователи могут заполнить один день независимо. Новый аккаунт создаётся без доступа к старым записям. Администратор Django — отдельная привилегированная роль.

## Существующая база
Перед обновлением сделана резервная копия. Миграция 0007 добавляет владельцев; 0008 присваивает существующие записи аккаунту, указанному в MEDIARY_LEGACY_OWNER, затем делает владельца обязательным. Приложение не присваивает данные первому зарегистрировавшемуся. 

Первичные данные входа находятся локально в LOCAL_ACCOUNT.txt. Файл, личная база и .django_secret_key исключены из Git. После входа можно сменить временный пароль через «Сменить пароль».

При переносе существующей базы на другой компьютер сначала создать нужного пользователя через Django shell, затем задать MEDIARY_LEGACY_OWNER и выполнить migrate. Для новой пустой базы переменная не требуется. Не удалять базу или миграции.

## Проверка
Открыть сайт без входа → форма входа. Зарегистрировать новый аккаунт → войти → пустой дневник. Войти в старый аккаунт → собственные записи. Попытка открыть чужой id возвращает 404. Выход выполняется только POST с CSRF. Пароли и сессии не передаются через URL.
