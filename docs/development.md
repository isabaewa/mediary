# Разработка и проверка изменений

## Окружение

Рабочие зависимости находятся в `requirements.txt`, инструменты разработки —
в `requirements-dev.txt`. Установка выполняется в виртуальное окружение проекта:

```cmd
venv\Scripts\python.exe -m pip install -r requirements-dev.txt
```

Версии инструментов зафиксированы для воспроизводимости. Для обычного запуска
приложения Ruff, Node.js и Playwright не требуются.

## Проверка одной командой

```cmd
venv\Scripts\python.exe scripts/check.py
```

Команда последовательно запускает линтер, проверку форматирования, Django check,
проверку отсутствующих миграций и серверные тесты. При первой ошибке возвращается
ненулевой код, следующие проверки не выполняются. Рабочая база не мигрируется;
серверные тесты используют отдельную тестовую базу.

Автоматическое форматирование и безопасные исправления импортов запускаются отдельно:

```cmd
venv\Scripts\python.exe -m ruff check . --fix
venv\Scripts\python.exe -m ruff format .
```

Правила находятся в `pyproject.toml`: Python 3.12, строки до 100 символов для
форматтера, сортировка импортов и базовые проверки корректности. Миграции исключены
из форматирования, чтобы не переписывать уже применённую историю схемы. Область
проверки ограничена исходниками проекта; локальные учебные материалы не изменяются.

## Серверные тесты по областям

```cmd
venv\Scripts\python.exe manage.py test diary
venv\Scripts\python.exe manage.py test diary.tests.test_auth
venv\Scripts\python.exe manage.py test diary.tests.test_services
```

| Модуль | Проверяет |
| --- | --- |
| `diary/tests/base.py` | Общие фикстуры без тестовых методов |
| `test_auth.py` | Регистрацию, доступ к своим данным, вход, сессии и выход |
| `test_medications.py` | CRUD препаратов и режимы курса |
| `test_schedule.py` | Согласование плана и сохранение истории |
| `test_health.py` | CRUD дневника, даты и оценку боли |
| `test_intakes.py` | Отметки приёма, JSON, CSRF и дополнительные приёмы |
| `test_history.py` | Главную страницу, архив и постраничную историю препарата |
| `test_integrity.py` | Ограничения моделей и общие проверки форм |
| `test_services.py` | Инварианты сервисов вне HTTP-запроса и откат при сбое |

Исходные 58 проверок сохранены по одному разу. В сервис добавлены отдельные проверки
владения, времени, источника препарата, атомарности и сохранения плановых слотов.

## Браузерные тесты

Playwright на JavaScript проверяет настоящее взаимодействие с тестовым HTTP-сервером Django.
Используется `StaticLiveServerTestCase`: он создаёт отдельную тестовую базу,
а каждый сценарий получает искусственные записи и новый контекст браузера.
Запущенное пользователем приложение и личная SQLite для этих сценариев не нужны.

Один раз установить Node.js 20 или новее, затем зависимости из `package-lock.json`:

```cmd
npm ci
```

Для отдельного Chromium сначала установить браузер:

```cmd
npx playwright install chromium
venv\Scripts\python.exe scripts/check.py --browser
```

На Windows можно использовать уже установленный Microsoft Edge без загрузки Chromium:

```cmd
venv\Scripts\python.exe scripts/check.py --browser --browser-channel msedge
```

Запуск только браузерного набора в Windows CMD:

```cmd
set MEDIARY_BROWSER_CHANNEL=msedge
venv\Scripts\python.exe manage.py test browser_tests
```

`browser_tests/test_components.py` создаёт данные и проверяет результат в БД.
`browser_tests/components.cjs` выполняет действия в настоящем браузере: режим и количество приёмов,
сохранение дневника, отметка и снятие пилюли без навигации, сетевая ошибка и повтор,
дополнительный приём с другим часовым поясом браузера, обычная форма без JavaScript.
Каждый сценарий выполняется на широком и мобильном экране. Вызовы на сервер настоящие;
перехватывается только специально проверяемая сетевая ошибка.

При отсутствии Node.js или Playwright браузерный набор завершается с инструкцией
по установке, а не сообщает об успешной проверке. Обычный запуск `manage.py test diary`
не требует браузера. Запуск `manage.py test` без метки собирает оба набора, поэтому
для него следует подготовить браузер. Вместо этого можно запускать все серверные
проверки командой `manage.py test --exclude-tag=browser`.

## Границы сервисов

`record_extra_intake` используется обоими HTTP-обработчиками дополнительного приёма.
Он повторно проверяет владельца и время, резервирует плановые слоты и атомарно
создаёт препарат с приёмом. Сервис возвращает модель либо исключение, не HTTP-ответ.
Форма отвечает за пользовательские ошибки ввода, представление — за redirect,
сообщение и преобразование недоступного препарата в 404.

`sync_intakes` по-прежнему вызывается вместе с сохранением курса внутри транзакции:
выполненные записи сохраняются, дополнительные приёмы не входят в ежедневную цель.
SQLite подходит для локального приложения, но её `select_for_update` не предоставляет
блокировку отдельных строк; массовые параллельные записи требуют отдельного решения
и проверки на выбранной серверной БД.

## Перед отправкой изменений

Проверить `git diff` и состав файлов. База, сессии, ключи, реальные учётные данные и
артефакты тестов не должны попадать в коммиты. Использовать искусственные данные
в тестах. Автоформатирование не заменяет просмотр изменения логики и результатов тестов.

Инструменты: [Ruff](https://docs.astral.sh/ruff/),
[Playwright](https://playwright.dev/docs/intro).
