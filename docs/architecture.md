# Структура проекта и компоненты Mediary

## Общая организация

Проект использует обычное для Django разделение Model–Template–View. Для текущего
размера достаточно одного приложения `diary`: препараты, приёмы и самочувствие
составляют одну предметную область. Делить каждый экран на отдельное Django-приложение
или вводить React ради компонентов не требуется.

| Расположение | Ответственность |
| --- | --- |
| `config/` | Настройки Django и подключение маршрутов приложения |
| `diary/models.py` | Модели, связи и ограничения базы данных |
| `diary/forms.py` | Преобразование и проверка пользовательского ввода |
| `diary/filter_forms.py` | Проверка параметров поиска, фильтров и сортировки |
| `diary/selectors.py` | Чтение списков с ограничением владельцем и условиями выборки |
| `diary/db_functions.py` | Unicode-регистр текста при поиске в SQLite |
| `diary/views.py` | HTTP-запросы, проверка владельца, формы и выбор ответа |
| `diary/auth_views.py` | Личный кабинет, вход, регистрация, пароль и сессия |
| `diary/services.py` | Запись дополнительных приёмов и пересчёт расписания |
| `diary/urls.py` | Соответствие адресов обработчикам, имена маршрутов |
| `diary/migrations/` | Версионируемые изменения схемы БД |
| `diary/tests/` | Серверные тесты по предметным областям |
| `browser_tests/` | Пользовательские сценарии с тестовым сервером и браузером |
| `scripts/check.py` | Общий запуск проверок кода, миграций и тестов |
| `templates/` | HTML-страницы и включаемые части форм |
| `static/js/` | Изолированное поведение компонентов в браузере |
| `static/css/` | Общие правила оформления и правила отдельных страниц |
| `docs/` | Архитектура, схема БД и описание учебных заданий |

Личный кабинет размещён в `templates/account/profile.html`. `ProfileForm` разрешает
редактировать только логин, имя, фамилию и почту текущего пользователя;
`account_summary_for` собирает его показатели. Доступ и проверки описаны в
[account.md](account.md).

Папка `templates/registration/` использует принятое Django расположение шаблонов
аутентификации. Общий каталог `templates` и общий `static` допустимы для одного
приложения. При добавлении независимых приложений их ресурсы следует разделять
подкаталогами с именами приложений, чтобы избежать совпадений имён.

## Компоненты браузера

Каждый JS-файл заключён в собственную функцию: внутренние переменные и обработчики
не попадают в глобальную область. Скрипты подключаются с `defer`, поэтому начинают
работу после разбора HTML. Страницы добавляют нужные скрипты через `extra_js`.

| Компонент | HTML | JavaScript | События и реакция |
| --- | --- | --- | --- |
| Шапка | `base.html` | `base.js` | `click`: повтор анимации на текущей главной |
| Форма препарата | `medications/fields.html` | `medication-form.js` | `change`, `input`, `click`, `toggle`: режим, слоты времени и очистка |
| Дневник | `diary/fields.html` | `health-entry.js` | `click`, `change`, `input`: выбор настроения, самочувствия и боли |
| Плановые приёмы | `dashboard.html` | `dashboard.js` | `submit`: POST, подтверждённый статус и прогресс; таймер: просрочка |
| Дополнительный приём | `quick_intake_fields.html` | `quick-intake.js` | `click`, `change`, `input`, `submit`: диалог, новый препарат и отправка |

`form.html` содержит общую оболочку: CSRF-токен, ошибки и кнопки действий.
Представление передаёт явный `form_kind` (`medication` или `health`), по которому
выбираются поля и скрипт. Тип компонента не определяется по наличию случайного поля.

Скрипт работает с полями только своей формы. Нативные поля Django — источник данных
для отправки: визуальные кнопки записывают в них значение и вызывают стандартное
событие. Один обработчик синхронизирует выбранную кнопку, подпись и `aria-pressed`.
Это предотвращает расхождение интерфейса при программном изменении поля.

## Отметка планового приёма

1. Форма `.intake-toggle` отправляет POST на именованный маршрут `toggle_intake`.
2. JavaScript отменяет обычную навигацию, берёт CSRF-токен из формы и отправляет
   `taken=true` или `taken=false` через `fetch` с `Accept: application/json`.
3. `toggle_intake_status_view` ищет запись с учётом владельца, проверяет значение
   статуса, сохраняет его и время приёма в транзакции.
4. Сервер возвращает `taken` и `taken_at`. Только после успешного ответа интерфейс
   обновляет кнопку, подпись и счётчик плановых приёмов.
5. При ошибке состояние не переключается, выводится сообщение, кнопка снова доступна.

Явный желаемый статус позволяет повторить запрос после потери ответа: уже выполненная
отметка не переключится обратно и её время не перезапишется. Без JavaScript обычная
форма работает через POST и redirect. Дополнительные приёмы не входят в ежедневную цель.

Поле `datetime-local` не хранит часовой пояс. Диалог получает активный пояс Django
через `data-time-zone` и формирует текущее время в нём, даже если браузер находится
в другом поясе. Ограничение будущего времени дополнительно проверяет сервер.

## Комментарии и сопровождение

- Docstring модуля описывает его ответственность, функции — контракт или существенный
  побочный эффект. Комментарии объясняют причины решений и ограничения.
- В шаблонах пояснения разработчику записываются через `{# ... #}` и не попадают
  в отданный HTML. Комментарии не должны содержать реальные личные сведения.
- Смена расписания выполняется вместе с `sync_intakes` внутри `transaction.atomic()`.
  Выполненные приёмы и дополнительные записи сохраняются.
- Проверки в браузере улучшают взаимодействие, но не заменяют проверку формы,
  авторизацию и ограничения БД.
- Новые изменения схемы оформляются новыми миграциями; применённые миграции
  не редактируются ради форматирования.

## Результат проверки и границы

Основное разделение ответственности соответствует обычной практике небольших
Django-проектов. При проверке были разделены встроенные JS-блоки, вынесены части форм,
устранены дублирующиеся обработчики выбора и неиспользуемый код синхронизации даты,
добавлены контракты модулей и пояснения неочевидных операций.

Тесты разделены по предметным областям. Один `views.py` пока достаточен: операции
дополнительных приёмов вынесены в `record_extra_intake` и используются повторно.
Списки препаратов и дневника разбиты на страницы по 20 записей; поиск и фильтры
сохраняются при переходах. Общий журнал пока загружается целиком; при большом количестве
записей ему также потребуется пагинация, как у истории препарата.

Настройки рассчитаны на локальную учебную демонстрацию (`DEBUG=True`, SQLite).
Это не готовая конфигурация публичного сервера: при размещении нужны настройки
хоста, HTTPS, production-секретов и обслуживания статических файлов. Проверка структуры
не заменяет нагрузочное тестирование и полный аудит безопасности.

## Проверка после изменения компонентов

```cmd
venv\Scripts\python.exe manage.py check
venv\Scripts\python.exe manage.py makemigrations --check --dry-run
venv\Scripts\python.exe manage.py test diary
```

В браузере проверить создание и редактирование обеих форм, режимы курса, количество
приёмов, очистку времени, начальное значение боли, синхронизацию выбранных кнопок,
отметку и снятие приёма, сетевую ошибку, диалог и отдельную страницу дополнительного
приёма. Повторить основные сценарии на узком экране. Данные для таких проверок должны
быть искусственными; личная база, ключи и учётные данные не включаются в Git.

Установка инструментов, запуск браузерных сценариев и команды форматирования:
[development.md](development.md).
